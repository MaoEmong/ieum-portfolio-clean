# 백엔드 사례 | 원인에서 실행 가능한 검증까지

이 문서는 서비스 v1의 코드·검증 기록을 선별한 **사후 사례 정리**입니다. [Spring 예제](../examples/backend-boundaries/README.md)는 그 판단을 검토하기 위해 새로 구성했습니다. 원본 서비스 코드, 실제 인프라, 당시 개발 순서를 그대로 재현하는 것은 아닙니다.

## 1. 파일이 없다는 사실과 파일을 읽지 못했다는 장애를 구분

### 관측과 원인

DB의 파일 참조와 기록 본문은 남아 있었지만 서버의 예상 경로에서 일부 원본을 찾을 수 없었습니다. 일반 I/O 오류로만 전달돼 앱도 원본 부재와 일시 조회 장애를 구분하지 못했습니다. 원본의 정확한 유실 시점까지 입증한 것은 아닙니다.

서버 인스턴스의 로컬 파일 수명과 DB 레코드 수명이 다르다는 점이 저장 방식 변경의 출발점이었습니다. private 객체 저장소로 파일을 분리하는 것과, 이미 없는 원본을 복구하는 것은 서로 다른 작업입니다.

### 대안과 구현 판단

| 대안 | 문제점·선택 이유 |
|---|---|
| 모든 읽기 실패를 404로 변환 | 권한 오류·버킷 문제·일시 장애까지 원본 유실로 오인하므로 채택하지 않음 |
| 저장소 HTTP 상태만 확인 | 공급자 측 404라도 객체 부재인지 버킷·경로 문제인지 확정할 수 없음 |
| 확정된 파일 부재만 도메인 오류로 변환 | 선택. 저장소 어댑터가 의미를 판정하고 HTTP 계층은 공개 가능한 오류 계약으로 변환 |

서비스에서는 실제 로컬 파일 부재와 저장소의 명시적인 객체 부재를 404로 분류했습니다. 권한·연결·버킷 부재·불명확한 404는 일반 서버 오류로 유지했습니다. 상세 원인·파일 키·내부 경로를 응답 본문에 넣지 않았습니다.

```text
파일 조회
  ├─ 성공                 → 바이트 전달 / 원본 불변
  ├─ 확정된 객체 부재      → 도메인 오류 → HTTP 404
  └─ 권한·연결·모호한 오류 → 서버 오류 → 내부 상세 비노출
```

공개 예제는 오류 분류를 가짜 DocumentStorage로 재구성합니다. 예제의 상태 코드 세분화·사용자 접근 대조군은 예제 자체의 계약이며, 서비스의 모든 오류 코드나 인증 구현을 복제한 것이 아닙니다.

### 무엇을 단정했나

- 정상 파일을 읽었을 때 응답 바이트와 저장 바이트가 모두 일치한다.
- 확정된 부재만 404이고, 권한·연결·불명확한 오류는 부재로 숨기지 않는다.
- 오류 응답에 내부 경로·원인 메시지가 포함되지 않는다.
- 가짜 저장소의 읽기가 실제 호출됐으며 추가 삭제·덮어쓰기·재업로드 호출은 없다.

당시 사후 기록에는 신규 백엔드 회귀 22개 중 6개가 기대 404·실제 500으로 실패했고, 수정 뒤 기존 저장소 검사와 함께 28개가 통과했다고 남아 있습니다. 서로 다른 실행 범위이므로 22개와 28개를 동일 테스트 집합의 수치로 비교하지 않습니다.

API 회귀와 별개로, 실제 스테이징에는 신규 합성 사진 1개를 올린 뒤 서버 재배포·앱 새 프로세스에서 재조회하고 바이트를 대조했습니다. **새 파일 1개의 보존 확인이며 기존 누락 원본 복구는 아닙니다.**

## 2. 설정 판정 테스트가 아니라 실제 기동을 검증

### 문제와 선택

개발용 인증은 로컬 개발과 테스트에는 필요하지만 배포 환경에서 활성화되면 안 됩니다. 저장소도 배포 환경에서 인스턴스 수명에 종속된 구성을 선택하지 못하도록 해야 했습니다.

개발 기능을 모두 제거하면 개발·테스트 흐름을 잃습니다. 배포 체크리스트만 두면 설정 누락을 기계적으로 막지 못합니다. 그래서 **개발 기능은 유지하고 배포 환경의 위험한 조합은 기동 단계에서 거부**했습니다.

서비스에는 인증 관련 가드와 저장소 구성 검사가 각각 존재합니다. 공개 예제에서는 이를 작은 기동 정책으로 모아 표현합니다. 실제 키 검증·인증 토큰·DB 배선은 포함하지 않습니다.

### 테스트가 초록색이어도 틀릴 수 있었던 이유

당시 테스트 주석과 검증 기록에는 다음 함정이 남아 있습니다.

1. **설정 우선순위:** 낮은 우선순위 기본값으로 넣은 테스트 설정이 앱 설정에 덮여, 의도한 위험 조건 자체가 만들어지지 않을 수 있었습니다.
2. **지연 초기화:** 기동 검사를 가진 빈이 생성되지 않으면 초기화 콜백도 실행되지 않습니다.
3. **무관한 컨텍스트 실패:** DB·리포지토리 배선을 깨뜨린 축소 테스트는 정책이 아니라 다른 원인으로 실패할 수 있었습니다.

따라서 순수 판정 함수만 검사하지 않고 실제 컨텍스트를 시작했습니다. 실패의 최하위 원인과 메시지를 확인하고, 정상 환경에서는 컨텍스트가 활성 상태이며 가드 빈이 실제로 존재하는지 대조했습니다. 중복 설정 키가 합쳐지는 문제도 피하도록 입력을 구성했습니다.

| 검사 | 잡으려는 결함 |
|---|---|
| 위험 조합의 판정 | 조건식·환경 분기 오류 |
| 실제 기동 실패 원인 | 가드 배선 누락, 무관한 실패를 성공으로 오판 |
| 정상 개발 기동 + 빈 존재 | 검사가 아예 실행되지 않은 거짓 성공 |
| 정상 배포 기동 | 모든 실행을 막아 통과하는 잘못된 방어 코드 |

공개 예제에는 실제 DB를 연결하지 않습니다. 선택한 정책의 Spring 생명주기를 확인하는 작은 컨텍스트이며, 서비스 전체 자동 구성의 통합 검증과는 다릅니다.

## 독자가 직접 검토할 수 있는 것

```sh
cd examples/backend-boundaries
mvn --batch-mode verify
```

예제 안내에는 의도적으로 잘못된 변형을 넣어 테스트가 실패하는지 확인하는 절차도 포함합니다. 이것은 **지금 만든 결함 주입 실험**이지 과거 서비스의 수정 전 코드를 공개한 것이 아닙니다. 일반 테스트 통과와 결함 탐지 여부를 따로 확인합니다.

[AI 협업 기록](ai-assisted-development.md)은 위 결과를 사용자 요구·AI 지원과 연결합니다. 실행 결과만으로 누가 코드를 작성했는지 추정하지 않습니다.
